## Відповідь на перший запит
Огляд файлів:

Frontend (index.html, style.css, script.js) — клієнтський додаток Meal Planner (планування харчування, рецепти з DummyJSON, стилі та скрипт).
Backend (server.js) — сервер на чистому Node.js (без Express), який початково містив роздачу статики з папки public/ та чужий API для вправ/тренувань (exercises).

Поточна структура та проблеми:

Повна відсутність зв'язку між частинами: фронтенд звертався напряму до стороннього API dummyjson.com та використовував браузерні Cookie.
Бекенд очікував файли інтерфейсу в папці public/, тоді як вони лежали в корені.

Де frontend зберігав дані:

Cookie (document.cookie): зберігався весь список плану страв у кукі mealPlan (функції savePlanToCookie() та getPlanFromCookie()).
Local / Session Storage: не використовувалися взагалі.
Локальні масиви в пам'яті: recipes = [] (список завантажених рецептів), mealPlan = [] (активний план), filteredPlan (тимчасовий масив для фільтрації).

Дані, які потрібно перенести на сервер:

План страв (mealPlan) — перенести з Cookie у файл data/data.json для зняття ліміту 4 КБ та надійного збереження.
Рецепти (recipes) — кешувати на сервері, щоб не залежати від стороннього сервісу.
Статистика — підраховувати загальну кількість страв і середній час на бекенді.

План об'єднання:

Крок 1: Створити папку public/ і перемістити туди index.html, script.js, style.css.
Крок 2: Переписати server.js під Meal Planner (додати REST API: /api/recipes, /api/plan, /api/stats із збереженням у data/data.json).
Крок 3: Рефакторинг script.js: видалити Cookie і налаштувати роботу через fetch() до власного бекенду.


## Які файли ШІ створив або змінив

### Створені файли:
`data/data.json` — локальне файлове сховище даних (база даних JSON) для збереження каталогу рецептів та тижневого плану харчування (`recipes`, `mealPlan`).
`routes/routes.js` — модуль маршрутизації REST API: обробка ендпоінтів для рецептів, плану та статистики, виклик відповідних сервісів та повернення коректних HTTP-статусів.
`services/service.js` — шар бізнес-логіки та доступу до даних: читання/запис у JSON-файл, взаємодія з зовнішнім API DummyJSON, CRUD-операції над планом та розрахунок статистики.
`utils/validation.js` — модуль серверної валідації вхідних даних: перевірка структури payload, білі списки днів тижня (`VALID_DAYS`) та прийомів їжі (`VALID_MEAL_TYPES`).
`package.json` — файл конфігурації Node.js-проєкту зі скриптами запуску (`npm start`, `npm run dev`).
`README.md` — детальна технічна документація проєкту, опис структури, інструкції із запуску та специфікація API.

### Змінені та реорганізовані файли:
`public/index.html` (переміщено з кореня до папки `public/`) — додано розмітку модального вікна підтвердження видалення (`#confirmModal`) та контейнер для спливаючих сповіщень (`#toastContainer`).
`public/script.js` (переміщено з кореня до папки `public/`) — повністю вилучено роботу з `document.cookie`, реалізовано взаємодію з бекендом через `fetch()`, додано клієнтську валідацію, захист від дублювання записів, інлайн-редагування страв, сповіщення Toast, стани `Loading...` та модальне вікно підтвердження видалення.
`public/style.css` (переміщено з кореня до папки `public/`) — додано стилі для Toast-сповіщень, анімованого спінера завантаження (`.spinner`), карток порожнього стану (`.empty-state`), форми редагування та модального вікна з бекдропом (`.modal-overlay`, `.modal-card`).

## Які тести були виконані

1. Функціональне тестування REST API та збереження даних:
   `GET /api/recipes`: перевірено автоматичне первинне завантаження з DummyJSON у локальну базу `data.json` та роботу фільтрації за назвою (`?search=`).
   `POST /api/plan`: перевірено додавання страви, повернення коду `201 Created`, збереження у файл `data/data.json`, а також відповідь `400 Bad Request` при передачі неповних або некоректних полів.
   `PUT /api/plan/:id`: протестовано зміну дня тижня та прийому їжі, оновлення у файлі, повернення `404 Not Found` для неіснуючого ID та `400 Bad Request` при спробі передати неприпустимі значення.
   `DELETE /api/plan/:id`: перевірено видалення страви з файлу бази даних та коректну відповідь `404 Not Found` у разі повторного запиту.
   `GET /api/stats`: перевірено динамічний розрахунок загальної кількості запланованих страв і середнього часу приготування.

2. Тестування клієнтського інтерфейсу (Frontend & UX):
   Перевірка блокування кнопки: під час відправки форми кнопка «Додати до плану» блокується (`disabled = true`, текст змінюється на `Loading...`), що унеможливлює створення дублікатів при подвійному кліку.
   Тестування Toast-сповіщень: перевірено появу зелених повідомлень при успіху (додавання, зміна, видалення) та червоних при помилках (не обрано день, серверна помилка).
   Тестування підтвердження видалення: перевірено роботу модального вікна — клік «Скасувати» або клавіша Escape скасовують операцію; клік «Видалити» надсилає `DELETE`-запит.
   Тестування персистентності: перевірено збереження стану після перезавантаження сторінки (F5) — дані успішно підтягуються з сервера, робота додатку більше не залежить від Cookie.
   Тестування порожніх станів: перевірено відображення інформативного блоку-підказки замість порожнього місця, коли у плані ще немає страв або нічого не знайдено за пошуком.



## Яку нову функцію було додано

1. Повна клієнт-серверна інтеграція (REST API):
    Замінено ненадійне локальне збереження в браузерних `Cookie` на серверне сховище в `data/data.json`.
    Реалізовано асинхронні виклики через `fetch()` для всіх операцій із даними.

2. Функція редагування існуючої страви (`PUT /api/plan/:id`):
    На фронтенді додано інлайн-режим редагування: кнопка «Редагувати» відкриває селектори зміни дня тижня та прийому їжі з кнопками «Зберегти» та «Скасувати».
    На бекенді реалізовано маршрут `PUT`, який валідує оновлені поля та зберігає зміни у файлі.

3. Інтерактивне підтвердження видалення:
    Створено анімоване модальне вікно із затемненням фону, яке запитує підтвердження перед видаленням конкретної страви із зазначенням її назви.
    Реалізовано закриття вікна по кнопці «Скасувати», кліку на бекдроп або клавішею Escape.

4. Дворівнева валідація даних:
    Frontend: перевірка вибору обов'язкових полів і попередження користувача про дублікати.
    Backend: валідація типів даних, довжини рядків, білих списків днів тижня та категорій їжі з поверненням стандартних HTTP-кодів (`201`, `400`, `404`, `500`, `502`).
